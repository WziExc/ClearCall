# 09 — 开发治理规范

> **用途**：确保开发过程中严格遵循项目标准，所有功能在所有场景下可正常运行。  
> **最后更新**：2026-06-08

---

## 一、开发铁律（不可违反）

### 1.1 标准文件优先
- 任何代码修改前，必须查阅对应的标准文件（见 CLAUDE.md 文件索引）
- 标准文件是唯一事实来源。如果发现标准与实现矛盾 → **改实现，不改标准**
- 如果标准本身需要修改 → 必须先更新标准文件，再改代码

### 1.2 一次一个阶段
- 严格按照 `04-development-plan.md` 的阶段顺序执行
- 不允许跨阶段开发。阶段 N 验收标准 100% 通过后，才进入阶段 N+1
- 阶段内任务允许调整顺序，但不允许跳过

### 1.3 验收即门禁
- 每个阶段末尾的"验收标准"是硬门禁
- 验收项未通过 → 该阶段不算完成，不可进入下一阶段
- 验收结果记录在当日开发日志中

### 1.4 双项目分支规则 🔴

> **cicall-classic/** 和 **clearcall-advanced/** 是同一项目的两个不同开发分支，**不是**独立项目。

| 目录 | 应用名 | Package ID | 定位 |
|------|--------|-----------|------|
| `clearcall/` | ClearCall | `com.clearcall.app` | 主开发线 |
| `clearcall-classic/` | ClearCall 经典 | `com.clearcall.classic` | 传统开发分支 |
| `clearcall-advanced/` | ClearCall 高级 | `com.clearcall.advanced` | 高级开发分支 |

**铁律**：
- 用户发起修改请求时，如果没有明确指出要修改哪个版本，**必须先询问确认目标版本**，不得擅自决定。
- 两条分支的修改应保持独立，不得混用代码。
- 修改后需分别构建验证对应的分支。

### 1.5 场景覆盖原则
- 每个功能必须覆盖以下场景：

| 场景类型 | 说明 | 示例 |
|---|---|---|
| **正常场景** | 一切正常时的行为 | Wi-Fi 下 2 人 720p 通话 |
| **边界场景** | 临界值行为 | 房间刚好 3 人时第 4 人加入 |
| **异常场景** | 出错时的降级行为 | 网络断开 → 自动重连提示 |
| **权限场景** | 权限被拒绝时的行为 | 摄像头拒绝 → 仅音频通话可用 |
| **空状态** | 无数据时的 UI | 无好友时显示引导文案 |
| **并发场景** | 多个事件同时发生 | 通话中来电 → 提示忙线 |

## 二、变更管理流程

### 2.1 三类变更

| 类型 | 定义 | 流程 |
|---|---|---|
| **A类：标准内变更** | 完全在现有标准范围内的开发工作 | 按标准执行，记录开发日志 |
| **B类：标准调整** | 需要修改标准文件但不改变核心需求 | 更新标准文件 → 更新开发日志 → 执行变更 |
| **C类：需求变更** | 新增/删除/改变核心功能 | 必须先与用户确认，更新标准文件全链路（需求→架构→UI→计划），再执行 |

### 2.2 变更影响检查清单

每次变更后，检查以下文件的连锁影响：

```
需求变更 (01) → 架构是否影响？    (02) → UI 规范是否要改？ (03)
              → 开发计划是否调整？ (04) → 编码规范是否涉及？ (05)
              → 数据 Schema 是否变？(06) → 协议是否变？     (07)
              → 国内适配是否影响？  (08) → 治理规范是否更新？(09)
```

### 2.3 遇到问题的处理等级

| 等级 | 情况 | 处理方式 |
|---|---|---|
| 🟢 绿 | 编码细节问题，标准已覆盖 | 自行解决，记录日志 |
| 🟡 黄 | 技术选型/实现方式在标准中未明确 | 参考 02 架构文档做出判断，记录决策理由 |
| 🟠 橙 | 标准文件之间有矛盾或标准与实现无法调和 | 停止当前任务，优先解决矛盾，更新标准 |
| 🔴 红 | 核心功能可能无法实现或严重偏离预期 | 立即停止，向用户报告并列出可选方案 |

## 三、质量保障规则

### 3.1 代码提交前检查

```
每次提交前（自查）：
□ flutter analyze 无 error（warning 允许但需在提交信息中说明）
□ 新增代码有对应测试（阶段 5 之前目标覆盖率 >50%，阶段 5 之后 >60%）
□ 相关标准文件未过时（如新增了功能但未更新需求文档 = 提交无效）
□ 提交信息格式：[阶段X] 简短描述
```

## 五、Firebase 配额监控

阶段 2 起，每次通话后记录以下指标，确保不超免费配额：

| 指标 | 免费配额 | 监控阈值 | 超出时处理 |
|---|---|---|---|
| 并发连接 | 100 | >80 → 警告 | 检查是否 onDisconnect 未生效 |
| 月下载量 | 10 GB | >8 GB → 警告 | 检查是否信令数据重复传输 |
| 存储量 | 1 GB | >800 MB → 警告 | 清理过期房间数据 |

## 六、开发日志规范

### 6.1 每日必须记录
- 当日完成事项（打勾）
- 当前阶段编号
- 遇到的新增决策（记录到决策日志）
- 下一步待办

### 6.2 决策日志
任何标准文件中未覆盖的技术决策，记录在当日日志的"📝 备注/想法"中，格式：
```
[决策] 选择 X 而非 Y，原因：Z。影响范围：A/B/C
```

## 七、上下文恢复指南

当会话上下文被重置后，新会话应按以下顺序恢复项目认知：

### 恢复步骤
1. **读取 CLAUDE.md** → 了解项目基本信息和文件索引
2. **读取 00-overview.md** → 理解项目定位和核心卖点
3. **读取 04-development-plan.md** → 确认当前开发阶段
4. **读取 dev-logs/ 最新日志** → 了解当前进度和待办
5. **读取当前阶段涉及的标准文件** → 开始工作

### 最小必读集（5 分钟内恢复）
- `CLAUDE.md`
- `00-overview.md`
- `04-development-plan.md`
- 最新 `dev-logs/YYYY-MM-DD.md`

### 完整必读集（15 分钟内完全恢复）

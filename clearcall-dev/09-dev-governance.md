# 09 — 开发治理规范

> **用途**：确保开发过程中严格遵循项目标准，保持代码质量。  
> **最后更新**：2026-06-10（精简版）

---

## 一、开发铁律

### 1.1 标准文件优先
- 任何代码修改前，查阅对应标准文件
- 标准 vs 实现矛盾 → **改实现**
- 标准本身需修改 → **先改标准，再改代码**

### 1.2 先规划、后执行
- ≥5 个文件修改或 ≥200 行新代码 → 先写方案到 `10-implementation-plans.md`
- 汇报方案 → 等待确认 → 执行
- 例外：纯查询 / 用户说"直接改" / 单行 bug 修复

### 1.3 一次一个阶段
- 按 `04-development-plan.md` 阶段顺序执行
- 阶段验收通过后才进入下一阶段

### 1.4 场景覆盖原则
每个功能覆盖：正常 / 边界 / 异常 / 权限拒绝 / 空状态

## 二、变更管理

### 三类变更

| 类型 | 定义 | 流程 |
|---|---|---|
| A类 | 标准内变更 | 按标准执行，记录日志 |
| B类 | 标准调整 | 更新标准 → 记录日志 → 执行 |
| C类 | 需求变更 | **必须先与用户确认**，更新全链路文档 |

### 问题分级

| 等级 | 情况 | 处理 |
|---|---|---|
| 🟢 | 编码细节，标准已覆盖 | 自行解决 |
| 🟡 | 标准未明确 | 参考架构判断，记录决策 |
| 🟠 | 标准间矛盾 | 停止，解决矛盾 |
| 🔴 | 核心功能无法实现 | 立即报告用户 |

## 三、质量保障

### 代码提交前检查

```
每次提交前：
□ flutter analyze 无 error
□ 新增代码有测试（如适用）
□ 相关标准文件未过时
□ 提交信息：[阶段X] 简短描述
```

### 测试要求

| 代码类型 | 单元测试 | Widget 测试 |
|---|---|---|
| 数据模型 | ✅ | — |
| 工具函数 | ✅ | — |
| 服务类 | ✅ | — |
| UI 组件 | — | ✅ |
| 通话界面 | — | ✅ |
